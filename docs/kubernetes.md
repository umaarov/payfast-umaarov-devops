# Kubernetes

Manifests are in `k8s/` and are applied with Kustomize, which is built into `kubectl`. They have been rendered and checked for structure, but not yet applied to a running cluster.

## What gets created

| Object | Count | Notes |
| --- | --- | --- |
| Namespace `logistics` | 1 | Pod Security Standard `restricted` is enforced |
| Deployment + Service + PodDisruptionBudget | 5 each | warehouse, tracking, delivery, order, api-gateway; 2 replicas each |
| StatefulSet `postgres` + headless Service | 1 | One server, 5 GiB volume, four databases created by the init script |
| ConfigMap `postgres-init` | 1 | The database init script, generated by Kustomize |
| NetworkPolicy | 8 | Default deny plus one allow policy per workload |
| Ingress `api-gateway` | 1 | Host `logistics.local`, class `nginx`, 1 MB body limit |

## Requirements

- A cluster and `kubectl` 1.27 or newer
- The images published by the CD workflow (push to `main` or a `v*` tag), at `ghcr.io/umaarov/logistics-<service>`
- For the Ingress: an ingress-nginx controller. Without one, use port-forward
- For the network policies to take effect: a network plugin that enforces them, such as Calico or Cilium. On a plugin that does not, the policies are accepted and ignored

## Deploy

Run from the repository root. The secrets are created from the same `.env` file that Docker Compose uses, so nothing secret is written into a manifest.

```powershell
.\scripts\init-env.ps1
kubectl apply -f k8s/namespace.yaml
kubectl create secret generic logistics-secrets --namespace logistics --from-env-file=.env
kubectl apply -k k8s
kubectl -n logistics rollout status statefulset/postgres
kubectl -n logistics rollout status deployment/api-gateway
```

If the repository, and so its packages, are private, create a pull secret first. Use a token that has only the `read:packages` scope:

```powershell
kubectl create secret docker-registry ghcr-pull --namespace logistics --docker-server=ghcr.io --docker-username=<github-user> --docker-password=<token>
```

Reach the gateway without an ingress:

```powershell
kubectl -n logistics port-forward service/api-gateway 8080:8080
```

Then use `http://localhost:8080` as in [docker.md](docker.md). The API key is `GATEWAY_API_KEYS` in `.env`.

## How a pod is configured

- Runs as user 10001 (PostgreSQL as 999), never as root, with a read-only root filesystem, all capabilities dropped, no privilege escalation, and the default seccomp profile. The only writable path is a small temporary volume.
- No service account token is mounted into any pod.
- Requests 100m CPU and 384 MiB; limits 1 CPU and 768 MiB. The JVM uses 75 percent of the limit.
- Three probes on the Spring Boot health groups: startup and liveness on `/actuator/health/liveness`, readiness on `/actuator/health/readiness`. Readiness includes the database, so a pod that lost its database leaves the Service without being restarted. The gateway lets these paths through without an API key.
- Rolling updates keep every old pod until a new one is ready (`maxUnavailable: 0`), pods get 40 seconds to finish requests, and a PodDisruptionBudget keeps one pod of each service during node maintenance.
- Pods are spread across nodes when more than one is available.

## Network rules

Everything is denied first, then only these paths are opened, all on port 8080 unless noted:

| From | To |
| --- | --- |
| ingress-nginx namespace | api-gateway |
| api-gateway | order, warehouse, delivery, tracking |
| order | warehouse, delivery, tracking |
| delivery | order, tracking |
| order, warehouse, delivery, tracking | postgres on 5432 |
| every pod | cluster DNS in kube-system |

Nothing else can reach a service or the database, including pods in other namespaces.

## Update, roll back, remove

Deploy a specific build by changing `newTag` in `k8s/kustomization.yaml` from `main` to the `sha-<commit>` tag that CD published, in a pull request, then apply again:

```powershell
kubectl apply -k k8s
```

```powershell
kubectl -n logistics rollout undo deployment/order-service
kubectl -n logistics rollout history deployment/order-service
```

```powershell
kubectl delete -k k8s
kubectl delete secret logistics-secrets --namespace logistics
```

Deleting the StatefulSet keeps its volume, so data survives until `kubectl -n logistics delete pvc data-postgres-0`.

## Limits of this setup

- One PostgreSQL pod is a single point of failure and has no backup. For production use a managed database or an operator with backups, and give each service its own server.
- TLS is not configured on the Ingress; terminate it with cert-manager or the cloud load balancer.
- There is no autoscaling; add a HorizontalPodAutoscaler once there are metrics.
- The pull secret and the API key are shared by everyone who has cluster access to the namespace.
